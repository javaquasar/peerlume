# Сценарии аудита отчётности BitTorrent tracker

## Назначение

Этот документ описывает контролируемые проверки, помогающие владельцу tracker
обнаруживать клиентов, которые отправляют противоречивые значения `uploaded`,
`downloaded` и `left`, нарушают жизненный цикл announce или совместно используют
одни учётные данные.

Проверки предназначены для локального или staging tracker, которым владеет оператор
теста. Они не включаются в рабочее поведение PeerLume. Производственный клиент
поддерживает только точную отчётность либо полное отключение tracker-коммуникации.

Базовые поля HTTP announce определены в
[BEP 3](https://www.bittorrent.org/beps/bep_0003.html), а бинарный UDP announce — в
[BEP 15](https://www.bittorrent.org/beps/bep_0015.html).

## Важное ограничение

Tracker видит только сведения, которые сообщает клиент. Протокол не содержит
криптографического доказательства реально переданных байтов. Клиент способен
отправлять внутренне согласованные, но ложные значения. Поэтому tracker может
надёжно выявлять противоречия и аномалии, но не может доказать точный фактический
объём только по announce.

Рекомендуемая реакция — накопление risk score, дополнительное наблюдение и ручная
проверка. Немедленная блокировка по одному эвристическому сигналу создаёт высокий
риск ложных срабатываний.

## Безопасная тестовая среда

1. Использовать отдельный passkey и отдельный тестовый torrent.
2. Разрешить audit harness только для `localhost`, приватной лабораторной сети или
   явно заданного staging hostname.
3. Записывать идентификатор тестового запуска в отдельное поле или журнал.
4. Не смешивать тестовые события с пользовательской статистикой.
5. Ограничить число announce и максимальную продолжительность теста.
6. После теста удалить или пометить тестовую статистику.
7. Не использовать реальные пользовательские passkey, IP или Peer ID.

## Нормальная модель сессии

Tracker должен группировать события как минимум по следующим значениям:

- account или passkey;
- `info_hash`;
- Peer ID;
- IP address и address family;
- listening port;
- transport: HTTP, HTTPS или UDP;
- время первого и последнего announce.

Для нормальной сессии ожидаются следующие свойства:

- `uploaded` и `downloaded` не уменьшаются;
- `left` не увеличивается;
- `left` находится в диапазоне от нуля до размера torrent;
- `completed` приходит только при `left == 0`;
- повторный `started` создаёт новую сессию или явно сбрасывает прежнюю;
- `stopped` завершает существующую сессию;
- скорость, вычисленная между announce, остаётся физически правдоподобной;
- HTTP и UDP события одной сессии не противоречат друг другу.

Перезапуск клиента, повторная проверка файлов, изменение выбранных файлов и потеря
локального состояния могут законно изменить наблюдаемую картину. Эти случаи следует
учитывать перед применением санкций.

## Сценарий 1: эталонная честная сессия

### Последовательность

1. Отправить `started` с известными начальными счётчиками.
2. Выполнить несколько периодических announce с монотонным ростом `downloaded` и
   уменьшением `left` на согласованную величину.
3. При достижении `left == 0` отправить `completed`.
4. Завершить сессию событием `stopped`.

### Ожидание

- risk score не увеличивается;
- tracker сохраняет одну непрерывную сессию;
- зачтённый объём совпадает с контрольными данными;
- `completed` учитывается один раз;
- повторная доставка одного announce не удваивает статистику.

Этот сценарий служит контрольной группой для всех последующих проверок.

## Сценарий 2: постоянный `downloaded=0`

### Последовательность

Клиент остаётся leecher, регулярно выполняет announce и получает peers, но во всех
сообщениях оставляет `downloaded=0`.

### Сигналы

- длительная активная сессия без изменения счётчиков;
- наличие исходящих peer connections при доступной серверу телеметрии;
- последующее `completed` без промежуточного роста `downloaded`;
- расхождение с предыдущими сессиями того же account.

### Защита от ложных срабатываний

Нулевой объём сам по себе допустим: peer может не найти источников, быть choked или
остановиться сразу после `started`. Сигнал становится сильным только вместе с
уменьшением `left`, событием `completed` или продолжительной активностью.

## Сценарий 3: `left` уменьшается без роста `downloaded`

### Последовательность

В каждом announce уменьшать `left`, оставляя `downloaded` неизменным.

### Сигналы

- изменение `left` и `downloaded` не согласовано;
- сумма наблюдаемого прогресса превышает изменение счётчика загрузки;
- аномалия повторяется в нескольких интервалах.

### Ожидание

Tracker повышает risk score после первого противоречия и усиливает оценку при
повторении. Для выбраночных загрузок допустима разница в трактовке `left`, поэтому
следует использовать допуск и не требовать строгого равенства байт.

## Сценарий 4: откат счётчиков

### Последовательность

После нескольких нормальных announce отправить меньшее значение `downloaded` или
`uploaded`, либо большее значение `left`.

### Сигналы

- нарушение монотонности внутри одной идентифицированной сессии;
- отсутствие нового `started`;
- прежний Peer ID, IP и listening port.

### Ожидание

Tracker не вычитает уже зачтённый объём, отмечает сессию как inconsistent и хранит
предыдущее максимальное подтверждённое значение. После явного нового `started`
возможен новый baseline, но частые сбросы сами становятся отдельным сигналом.

## Сценарий 5: некорректный `completed`

### Варианты

- `completed` при `left > 0`;
- `completed` без ранее наблюдаемого `started`;
- несколько `completed` для одной сессии;
- `completed`, после которого `left` снова становится больше нуля.

### Ожидание

Tracker не увеличивает глобальный completion count повторно, отмечает несогласованное
событие и повышает risk score. Отсутствие `started` оценивается мягче: tracker мог
перезапуститься или потерять часть краткоживущего состояния.

## Сценарий 6: физически неправдоподобный скачок

### Последовательность

Между двумя близкими announce резко увеличить `downloaded` или `uploaded` на объём,
требующий скорости выше настроенного лабораторного предела.

### Расчёт

`observed_rate = counter_delta / elapsed_seconds`

Порог должен учитывать задержку доставки, объединение событий, быстрые локальные
сети, seedbox и восстановленное состояние. Нельзя использовать один глобальный
порог для всех пользователей.

### Ожидание

Событие получает низкий или средний вес. Высокий вес допустим только при повторении
и наличии дополнительных противоречий.

## Сценарий 7: частая смена Peer ID

### Последовательность

Сохраняя account, `info_hash`, IP и port, отправлять announce с новыми Peer ID.

### Сигналы

- большое число Peer ID за короткий период;
- перекрывающиеся активные сессии;
- каждый новый идентификатор начинает с удобного baseline;
- одинаковая сигнатура поведения у всех идентификаторов.

### Защита от ложных срабатываний

Peer ID может законно измениться после переустановки, смены клиента или настройки
privacy. Оценивается частота и одновременность, а не сам факт изменения.

## Сценарий 8: совместное использование passkey

### Последовательность

Одновременно выполнять announce одного account с нескольких тестовых IP, Peer ID и
портов, превышая настроенный лимит.

### Сигналы

- географически или сетево несовместимые одновременные сессии;
- слишком много активных IP, ASN или устройств;
- одна и та же пара `info_hash`/account с большим числом peers;
- резкая смена IP без завершения предыдущей сессии.

### Ожидание

Tracker применяет отдельное правило account sharing. NAT, VPN, dual-stack и
динамические адреса требуют допустимого окна и не должны автоматически считаться
нарушением.

## Сценарий 9: нарушение порядка жизненного цикла

### Варианты

- `stopped` без активной сессии;
- периодический announce после `stopped` без нового `started`;
- постоянные повторные `started`;
- исчезновение без `stopped`;
- `completed` после истечения session timeout.

### Ожидание

Tracker корректно переживает потерю UDP пакетов и аварийное завершение клиента.
Отсутствие `stopped` не является нарушением. Повторяющиеся последовательности,
используемые для сброса baseline, повышают risk score.

## Сценарий 10: рассинхронизация HTTP и UDP

### Последовательность

Для одной логической сессии чередовать HTTP и UDP announce с противоречивыми
счётчиками, событиями или listening port.

### Сигналы

- одинаковые account, `info_hash` и Peer ID имеют разные baselines;
- один transport сообщает завершение, второй продолжает leecher-сессию;
- counters откатываются при смене transport;
- UDP transaction ID или action не соответствует запросу.

### Ожидание

Tracker объединяет transport events только при достаточном совпадении ключей.
Переход между IPv4 и IPv6 либо HTTP и UDP не должен сам по себе создавать нарушение.

## Дополнительные проверки устойчивости

Audit harness также должен проверять обработку malformed и повторных пакетов:

- отсутствующие обязательные параметры;
- переполнения и отрицательные текстовые значения;
- слишком длинные Peer ID, query string и failure reason;
- неизвестные event;
- неверные UDP action и transaction ID;
- повтор announce после сетевого timeout;
- перестановка и повторная доставка UDP пакетов;
- превышение rate limit;
- запрос с заблокированного IP.

Такие проверки относятся к надёжности parser и transport, а не к доказательству
нечестной статистики.

## Пример risk score

Конкретные веса должны настраиваться по статистике собственного tracker. Начальная
модель может выглядеть так:

| Сигнал | Баллы |
|---|---:|
| Однократный откат счётчика | 25 |
| Повторный откат в той же сессии | 40 |
| `completed` при `left > 0` | 35 |
| Уменьшение `left` без роста `downloaded` | 20 |
| Повторяющееся несогласованное изменение | 35 |
| Неправдоподобная скорость | 10 |
| Частая смена Peer ID | 15 |
| Превышение лимита одновременных IP | 30 |
| Рассинхронизация HTTP/UDP | 20 |
| Нарушение rate limit | 10 |

Пример реакции:

- `0–29`: сохранить наблюдение;
- `30–59`: усилить журналирование и сократить период повторной оценки;
- `60–89`: временно ограничить сессию и отправить на проверку;
- `90+`: временная блокировка с возможностью пересмотра.

Баллы должны затухать со временем. Постоянная пожизненная сумма создаёт ложные
блокировки из-за старых сбоев.

## Что сохранять в журнале

Для расследования достаточно хранить:

- timestamp и transport;
- account ID или необратимый внутренний идентификатор passkey;
- `info_hash`;
- Peer ID;
- IP, address family и port;
- event;
- counters до и после нормализации;
- interval между событиями;
- сработавшие правила и добавленные баллы;
- tracker response status;
- идентификатор audit run.

Сам passkey и полный credential-bearing URL не должны попадать в журнал.

## Критерии прохождения

Tracker проходит аудит, если:

1. Эталонная сессия не получает подозрительный score.
2. Повторные announce не удваивают статистику.
3. Откат counters не уменьшает уже зачтённые значения.
4. Некорректный `completed` не увеличивает completion count.
5. Потерянный `stopped` не приводит к автоматической блокировке.
6. Каждый аномальный сценарий оставляет объяснимую запись правила.
7. Ни журнал, ни diagnostics не содержат passkey.
8. HTTP и UDP используют одинаковую модель нормализации counters.
9. Rate limits не мешают нормальной сессии.
10. Оператор может отменить автоматическое решение и восстановить account.

## Ручной audit-клиент

Утилита `tracker-audit` реализует один контролируемый announce за запуск. Она
принимает явные значения `uploaded`, `downloaded` и `left`, сохраняет стабильный
Peer ID между запусками по аргументу `--peer-id` и возвращает полученный список
IPv4 peers в JSON. Это позволяет вручную воспроизвести сценарии 1–6, не добавляя
ложную отчётность в production-клиент.

По умолчанию разрешён только loopback. Для staging требуется передать точное имя
узла через `--allow-host`; URL tracker с passkey рекомендуется задавать переменной
`PEERLUME_AUDIT_TRACKER_URL`, чтобы он не оказался в списке аргументов процесса.
Каждый запуск отправляет ровно один announce.

## План дальнейшей автоматизации

Следующий этап для `tracker-audit` — именованные многошаговые сценарии, фиксированный
seed, итоговый JSON отчёт и ненулевой exit code при нарушении ожидаемых инвариантов.
Для staging host по-прежнему требуется явный allowlist и отдельный тестовый passkey.

Рекомендуемый порядок автоматизации:

1. Эталонная HTTP сессия.
2. Сценарии counters 2–6.
3. Жизненный цикл и смена Peer ID.
4. Account sharing.
5. UDP transport и HTTP/UDP рассинхронизация.
6. Malformed, timeout, retry и rate-limit проверки.
7. Повторный прогон после каждого изменения tracker accounting.
